# design/ · 设计稿目录

> **这里的 .html 是「可交互的设计稿」，不是产品代码。**
> 程序方案尚未确定，所以本目录不承担任何工程质量责任。
> **没有版本号。做到的就是最终版，旧的已删除。**

---

## 设计稿是什么

用浏览器能打开的单文件 HTML，目的是：
- 把**布局、间距、字重、颜色、层级**说到能照着实现的程度
- 把**交互流程**演出来（点击切换、悬停状态、状态变化）
- 用来做**设计评审**，而不是用来交付

## 设计稿不是什么

| 不是 | 说明 |
|---|---|
| ❌ 不是组件库 | 样式全部内联写死，没有抽 token，没有复用 |
| ❌ 不是可维护代码 | 没有类型、没有测试、没有错误处理 |
| ❌ 不是性能基线 | 图片走 CDN，动画不做优化，只为好看 |
| ❌ 不是最终视觉 | 每一版都可能被推翻 |

## 数据规则

**七屏里有三屏用真实数据**（`home.html`、`report.html`、`timeline.html`），其余四屏是构造样本。
构造样本也不是随便填的：

- 数字之间要**自洽**：伤害占比之和 ≈ 100%，承伤与阵亡次数不能矛盾
- 要包含**极端样本**：一定要有一个 0/12/3 的，也要有一个 2/8/21 的
- 要包含**边界情况**：数据缺失、重开局、全员平庸无人可骂

## home.html：首页，也全部读数据

数据包由 `tools/build-home-fixture.py` 生成。它**直接 import 报告页那套评分函数**
（`build-report-fixture.py`），所以首页显示的分数和点进去看到的完全一致，
不会出现「首页 42 分、详情 39 分」。

### 页面上有什么，凭什么

| 元素 | 依据 |
|---|---|
| 名字 + `#tag` | `current-summoner` 的 `gameName` / `tagLine` |
| 头像 | `profileIconId` → CommunityDragon `profile-icon/{id}`（**不是英雄头像**） |
| 等级 673 | `summonerLevel` |
| **未定级** | `queueMap` 里所有队列 `tier` 为空时的**正常显示** |
| 重随 0/250 | `rerollPoints.currentPoints` / `pointsToReroll` |
| 已记录 N 局 | 本地累计的对局数 |
| 三个大数 | 胜率 / 场均 KDA / 平均评分，全部按**实际局数**算，文案跟着变（「近 1 局胜率」） |
| 最近战报行 | 每行 = 那局的英雄、KDA、时长、评分、角色标签 |
| 汇总条 | 胜/负、当过蛆王次数、场均阵亡 |

### 两个刻意为之的地方

**① 段位空着就写「未定级」，不编。** 本号 6 个队列全空——纯大乱斗号不打排位。
把那里写死成一个段位名，等于对多数用户显示假数据。

**② 只有一局就只显示一行。** 现在就是真实的一行（时光守护者 2/8/41）。
记录多了自然会长，不留占位骨架屏。

### 角色标签的词表

首页每行末尾的标签，和报告页三栏**不完全是一套**（报告页只有 3 档，这里要分得更细）：

| 标签 | 条件 |
|---|---|
| 蛆 | 本队风险轨第一（与报告页同一判定） |
| 尽力 C | 本队综合分第一 |
| 最扛 | 本队团队轨第一（承伤/控制/治疗） |
| 大腿 | 输出轨 ≥ 80 但不是第一 |
| 工具人 | 其余 |

## report.html：结算页，全部读数据

页面里**没有一个写死的数字**。数据包由 `tools/build-report-fixture.py` 从
`fixtures/capture/2026-10-26T19-26-49` 生成（17 KB），内嵌进 HTML，所以双击即可打开。

**字段级对照表见 `docs/12-data-dictionary.md` §G。**

### 页面上有什么，凭什么

| 区块 | 内容 | 依据 |
|---|---|---|
| 头部 | 胜负、53:67、全员 KDA、金币差、塔数 | `teams[].isWinningTeam` / `stats` |
| 对阵阵容 | 10 人按**队内综合分**排序，每人三条轨 | 见下 |
| 中间时间轴 | 崩盘刻痕（红=我方/灰=敌方）+ 塔/水晶/团灭 | `ChampionKill` / `TurretKilled` / `Ace` |
| 三栏结论 ×2 | **敌我各一组**：尽力 C / 蛆 / 不团队 | 三条轨各自的极端值，见下 |
| 崩盘记录 | 11 次事件，标红的是「在犯罪」那个人发起的 4 次 | 崩盘聚类 |
| 详情条 | 6 项指标 + 4 枚符文 + 出装 + 召唤师技能 | `stats` / `PLAYER_AUGMENT_*` / `items` / `spell1Id` |

### 三栏判定的口径

**敌我各算一套，绝不跨队混排**——两队总伤害差 39%，放一起比就是错的。

| 栏 | 判定 | 约束 |
|---|---|---|
| 尽力 C | 队内**综合分**第一 | 不一定伤害最高：坦克靠团队轴也能拿 |
| 蛆 | 队内**风险轨**第一 | 头像打圆形红印章；评分并列时按崩盘发起次数、阵亡数排序 |
| 不团队 | 队内输出轨 ≥60 的人里，**团队轨最低** | 必须排除已当选 C 和蛆的人，否则一队三人只剩两个人可选 |

排序用综合分而不用输出轨，是为了让三栏落在三个人身上：若 C 也按输出排，
"伤害第一"和"只会输出"会是同一个人，三栏变成两栏。

### 三条轨怎么算

```
输出轨 = totalDamageDealtToChampions 的队内占比 ÷ 队内峰值
团队轨 = (承伤占比×0.5 + 控制占比×0.3 + (治疗+护盾)占比×0.2) ÷ 队内峰值
风险轨 = (崩盘发起×22 + 阵亡×2.2) ÷ 队内峰值
综合分 = 输出×0.42 + 团队×0.33 − 风险×0.35      ← 只用于排序
```

**全部在队内归一**。两队总伤害差 39%，跨队比较会误导，所以敌方只在敌方内部比。

### 崩盘事件的定义

```
窗口 W = 12 秒
1. 每次击杀看其后 12 秒：本队再死 ≥2 且敌方死亡 ≤ 本队 → 记一个崩盘窗口
2. 时间重叠的窗口合并为同一次事件（否则一波团灭会算 5 次）
3. 事件归因给最先阵亡的那个人
```

本局 18 个窗口合并成 11 次事件：我方 7 次、敌方 4 次。

### 页面明确不做的事

| 没有 | 为什么 |
|---|---|
| 死亡位置图 | 实时数据**没有坐标**，要 `game-timelines` 的 `position{x,y}`，本抓包未采集 |
| 视野分 / 补刀效率 | 大乱斗 `visionScore` 恒为 0，补刀无战术含义 |
| 跨队伤害排名 | 两队总伤害差 39%，比了会误导 |

## timeline.html：对局回放

不画界面，是把一场真实对局**回放**出来：10 条泳道 + 可拖拽时间轴 + 实时状态面板。

| 数据 | 来源 |
|---|---|
| 死亡区间（起止秒） | `ChampionKill.EventTime` + `playerlist.respawnTimer`（中位数推算） |
| 击杀 / 助攻 | `eventdata` 的 `KillerName` / `VictimName` / `Assisters` |
| 团战区间 | 击杀间隔 ≤10 秒的聚类 |
| 推塔 / 破水晶 / 团灭 | `TurretKilled` / `InhibKilled` / `Ace` |
| 等级曲线 | `playerlist.level`，每 5 秒采样 |
| 装备购买时刻 | `playerlist.items` 逐帧差分（170 次变动）→ `items.json` 查名与总价 |
| 玩家身份与终局战绩 | `eog-stats-block` 的 `teams[].players[]` |

**装备这条线**：金色方块 = 成装，金色细线 = 组件（会被合成掉）。悬停看「时间 · 装备名 · 总价」。

三个已验证 / 已发现的点：
- **购买与死亡强相关**：73% 的装备变动发生在死后 45 秒内，符合「大乱斗只能死着买」
- **不能把装备价格累加当花费**：组件被合成后会重复计算（买了 32,887，实际只花 22,600）
- 时间线算出的最终装备与 `eog` **逐人一致（10/10）**；`eog` 的 `items` 里 `0` 表示空槽

**死亡区间准不准，用 `eog.totalTimeSpentDead` 交叉校验：10 人总误差 2.1%。**

> 用法：打开自动播放；`?t=620` 跳到第 10:20；空格暂停、←/→ 前后 5 秒；点时间轴任意位置跳转。

### 数据来源：96% 实时

顶栏「数据源」按钮会把来源摊开：

| 来源 | 内容 |
|---|---|
| **实时**（liveclientdata，2 秒轮询） | 阵亡区间、击杀/助攻、团战、推塔破水晶团灭、等级、装备、KDA、比分、存活人数 |
| **赛后**（eog-stats-block） | **只有两项**：行序（按总伤害降序）、胜负判定 |
| **静态资产**（本地 LCU） | 英雄名/头像、装备名与总价 |

**行序为什么必须赛后**：实时拿不到伤害。按 KDA 排会让 10 人里 8 人位置变，辅助（41 助攻）会被顶到第一。

### 实时模式

点「实时模式」切到对局进行中的形态，差异是被迫的：

| 项 | 回放 | 实时 | 为什么 |
|---|---|---|---|
| 横轴 | 固定 0 → 19:04 | **0 → 已进行**，随时间变长（≤3 分钟用 30 秒刻度） | 不知道会打多久 |
| 行序 | 按总伤害降序 | **按英雄 ID 固定** | 实时无伤害；行跳动会盯不住 |
| 胜负徽章 | 我方胜利 / 失败 | **进行中** | 不知道结果 |
| 总时长 | 19:04 | **—** | 不知道终点 |
| 进度条 | 可拖 | **不可拖** | 不能跳到未来 |
| 跨度变化 | 无 | 每 60 秒扩一次，**260ms 过渡** | 硬跳会晕 |

**实时模式的硬缺口还是伤害**：承伤、治疗、控制、符文全部没有，所以「谁在 C / 谁在犯罪」
在局内做不了——只能给节奏（谁死、几打几、出装进度）。

> `?live=1` 可直接进实时模式。

## 转成工程时必须重做的事

等程序方案定了，这些**全部要重做**，不能搬运：

| 项 | 设计稿现状 | 工程要求 |
|---|---|---|
| 颜色 | 每个文件重复声明一遍 `:root` | 抽成唯一 token 文件 |
| 布局 | 绝对像素写死 | 响应式 + 最小窗口适配 |
| 组件 | 每个页面重新写一遍 | 抽成组件，props 化 |
| 数据 | 内嵌一个 JSON 常量 | 走 IPC，接状态机 |
| 图片 | CDN 直连 | 本地缓存 + 失败降级 |
| 动画 | CSS animation | 统一 motion 层 + reduced-motion 全局开关 |
| 无障碍 | 只做了一部分 | 完整键盘导航 + 语义标签 + 对比度校验 |

> 换句话说：设计稿的价值在「长什么样、怎么动、点哪里会发生什么」，不在「怎么写」。
